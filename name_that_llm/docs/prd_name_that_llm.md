# PRD — Name That LLM
Версія: 1.0 · Дата: 25.10.2026 · Мова реалізації: Python
Статус: готовий до старту розробки; правила участі й актуальні дані перевіряються на етапі 0.

**Source of truth:** Поточні офіційні сторінки Kaggle Overview, Data та Rules
мають перевагу над цим PRD у разі розбіжностей. Усі актуальні конкурсні факти,
джерела й дати перевірки фіксуються в `docs/competition.md`.

## 1. Мета
Створити відтворювану систему, яка визначає модель-автора тексту й формує валідну конкурсну submission. Основний продукт — експериментальний ML pipeline та автономний Kaggle Notebook, а не вебзастосунок.
Користувач: один розробник із досвідом Data Engineering та обмеженим часом.
Бізнес-результат: перевірити конкурентність підходу з контрольованими витратами; призовий результат не є критерієм технічної готовності.

## 2. Зовнішні умови
За перевіреною офіційною сторінкою:
- Класифікація автора серед 18 LLM; метрика — balanced accuracy, тобто середній recall класів.
- Основний пул $50,000: десять призів по $5,000.
- Вступ і формування команд: до 06.01.2027; фінальна подача: до 13.01.2027, 23:59 UTC.
- Подача через Kaggle Notebook; інтернет вимкнено; ліміт CPU або GPU Notebook — 9 годин.
- Результат: submission.parquet з колонками id та model.
- Поточний Kaggle Data описує `train.csv` з 2,699 прикладів на 150 prompts та
  `test.csv` із трьома інтерактивними прикладами; прихований rerun має приблизно
  4,000 рядків із prompts, яких немає у train.
- Submission має містити один рядок на кожний `id`; дозволені значення `model`
  наведені в `docs/competition.md` і `configs/baseline.yaml`.
- Kaggle дозволяє безкоштовні публічні зовнішні дані, включно з pretrained
  models; платна API-генерація потребує окремого уточнення правил.

Перед моделлю перевірити актуальні правила, ліцензії завантажених даних,
територіальну доступність та умови виплати. Офіційна Kaggle Data сторінка
описує розмічений train; локальне отримання й схема все одно мають пройти audit.
Якщо дозволені розмічені дані недоступні, supervised baseline заблокований.

## 3. Обсяг MVP
Входить:
1. Інвентаризація даних і перевірка схеми.
2. Аналіз дублікатів, довжин текстів, мов, класів та джерел.
3. Локальна валідація з контролем витоків.
4. Baseline TF-IDF + лінійний класифікатор, якщо доступні мітки.
5. Пакування offline inference і одна валідна конкурсна подача.
6. Звіт про якість, помилки, час та ресурси.

Поза MVP: fine-tuning великої LLM, платна масова генерація корпусу, AutoML-пошук без бюджету, API inference у конкурсному Notebook, вебінтерфейс.

## 4. Функціональні вимоги
FR-01. Адаптер читає фактичні конкурсні файли; назви колонок визначаються схемою, не вигадуються. Невідома схема дає зрозумілу помилку.
FR-02. Raw-дані незмінні. Manifest містить джерело, дату, ліцензію, checksum і кількість рядків.
FR-03. Профайлер рахує розподіл класів, мов, довжин, exact/near duplicates. Навчальні та тестові мітки ніколи не змішуються.
FR-04. Split групує однакові prompts, варіанти одного запиту та дублікати, коли відповідні поля доступні. За відсутності prompt_id використовуються доступні provenance-поля та кластери схожих текстів; залишковий ризик документується.
FR-05. Усі learned перетворення навчаються тільки на train fold. Заборонено випадковий row split як єдине підтвердження якості.
FR-06. Baseline порівнює dummy classifier, word TF-IDF, char TF-IDF та їх комбінацію; LinearSVC або logistic regression. Гіперпараметри задаються конфігом.
FR-07. Метрики: balanced accuracy основна; macro F1, recall по класах, confusion matrix додаткові. Фіксуються seed, split hash, config, dataset hash, commit.
FR-08. Експортований inference читає test.csv та записує рівно один рядок на кожен id, з точними labels із офіційного allowlist.
FR-09. Валідація артефакту перевіряє schema, null, дублікати, відсутні та зайві id, недопустимі класи.
FR-10. Notebook не завантажує мережеві залежності. Моделі й пакети, яких немає в середовищі, додаються як дозволені offline artifacts.

## 5. Архітектура й інтерфейси
Стек: pandas, pyarrow, scikit-learn, scipy; YAML-конфіги; pytest. Версії зафіксувати після smoke test у Kaggle.
Структура:
- src/ntllm/{data,validation,features,train,evaluate,predict,export}.py
- configs/baseline.yaml
- notebooks/submission.ipynb
- tests/; docs/; artifacts/; reports/

CLI, який потрібно реалізувати:
- python -m ntllm audit --config configs/baseline.yaml
- python -m ntllm train --config configs/baseline.yaml
- python -m ntllm evaluate --run-id RUN_ID
- python -m ntllm predict --model MODEL_DIR --input TEST_CSV --output submission.parquet
- python -m ntllm validate-submission --input submission.parquet --test TEST_CSV

Run-артефакти: config.yaml, manifest.json, split_assignments.parquet, metrics.json, predictions_oof.parquet, model artifact, error_analysis.md. OOF означає прогнози лише на даних, які відповідна fold-модель не бачила.

## 7. Acceptance criteria та перевірки
- На чистому середовищі документовані команди відтворюють audit, навчання й inference.
- Жодна група split не перетинається між train/validation; тест перевіряє це на fixture.
- Preprocessing не fit-иться на validation/test.
- Метрики зберігаються для dummy і baseline; числову ціль встановити після первинного вимірювання. Uniform guessing має очікувану balanced accuracy 1/18, але одного перевищення цього рівня недостатньо для конкурентності.
- Для однакового model artifact і входу прогнози ідентичні.
- Валідатор ловить усі перелічені порушення submission.
- Повний notebook завершується в межах офіційного runtime з виміряним запасом; рекомендований внутрішній поріг — не більш ніж 80% ліміту.
- Є хоча б одна прийнята подача; локальний результат без подачі позначається як «local-ready».
- Secret-и, сирі приватні дані й великі моделі не потрапляють у git.

## 8. Рішення після першого спринту
Продовжувати, якщо baseline відтворюється, split надійний, є напрям покращення і ресурсний бюджет прийнятний. Якщо public LB різко вищий за local CV — дослідити leakage та domain shift. Не оптимізувати лише public LB.
Кожен наступний експеримент має гіпотезу, одну основну зміну й порівняння на фіксованому split. Зміна split потребує повторного запуску baseline.
Ризики: відсутність train, prompt leakage, різні домени текстів, overfit на LB, обмеження зовнішніх даних, непідтверджена eligibility.
